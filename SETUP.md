# SETUP: как агенту развернуть штаб и память на машине пользователя

Этот документ написан для агента, а не для человека. Пользователь открыл тебя в этом репозитории и попросил помочь с настройкой. Ты знаешь его машину лучше, чем автор шаблона: систему, оболочку, установленных агентов, где что лежит. Поэтому здесь нет готовых путей и конфигов под конкретную систему. Здесь описано, чего нужно добиться в каждой фазе, что выяснить у пользователя, что сделать и как проверить, что получилось.

Что получит пользователь в конце:

- **Доктрину** — единые правила поведения для всех его агентов в одном файле `doctrine/AGENTS.md`, подключённом к каждому агенту ссылкой.
- **Штаб** — этот репозиторий, ставший его приватным: реестр проектов, задачи в GitHub Issues, решения, уроки, скиллы.
- **Память** — поиск по истории всех сессий агентов и по документам проектов через QMD, локальный поисковик по markdown.

Как это устроено и почему именно так, объясняют `README.md`, `AGENTS.md` и `docs/adr/`. Прочитай их перед началом, это займёт несколько минут и сэкономит вопросы.

## Правила этой настройки

Ты меняешь рабочую машину человека, поэтому действуют границы доктрины. Перед каждой фазой скажи пользователю одним абзацем, что сейчас изменится и в каких файлах, и дождись «ок». Внутри фазы работай сам: пользователю отдаются только шаги, которые без него сделать нельзя (вход в аккаунт, пароль, подтверждение в окне системы).

Ничего существующего не перезаписывай молча. Если у пользователя уже есть глобальные инструкции агента, настройки или скиллы, сначала сделай копию рядом с датой в имени, потом объединяй, а итог покажи. Секреты в репозиторий не попадают никогда.

Каждая фаза заканчивается проверкой, и проверка должна уметь упасть: там, где это возможно, сначала убедись, что до изменения она даёт отрицательный результат. «Файл на месте» проверкой не считается.

Веди список фаз так, чтобы пользователь видел, на какой ты сейчас. В конце отдай сводку: что установлено, где лежит, что проверено и что нет.

## Фаза 0. Разведка (только чтение)

Выясни и коротко доложи пользователю:

1. Система и оболочка; есть ли `git`, `python3` не ниже 3.10, `node` не ниже 22 (нужен QMD), `gh` и выполнен ли в нём вход (`gh auth status`).
2. Какие агенты установлены и где их настройки: Claude Code (`~/.claude/`), Codex (`~/.codex/` или `$CODEX_HOME`), другие. Для каждого: где он читает глобальные инструкции, где скиллы, как подключаются MCP-серверы (стандартный способ дать агенту внешний инструмент), есть ли хук конца сессии.
3. Что уже лежит в глобальных инструкциях каждого агента. Это личные правила пользователя, их нужно сохранить.
4. Стоит ли уже QMD (`qmd --version`, `qmd collection list`) и откуда: глобальный пакет или плагин агента.

Затем задай вопросы, на которые ответ даёт только пользователь, с вариантами и твоей рекомендацией:

- где будет жить штаб (рекомендация: `~/HQ`, на это имя рассчитаны все файлы шаблона);
- как назвать его приватный репозиторий на GitHub;
- каких агентов подключать;
- какие проекты завести в реестр сразу (имя, путь, репозиторий);
- какие папки с документами и заметками добавить в поиск, кроме истории сессий. Например, хранилище Obsidian или `docs/` проектов. Предупреди, что индекс локальный, но в него не стоит класть папки с секретами и выгрузками чужих персональных данных.

## Фаза 1. Репозиторий штаба

1. Создай приватный репозиторий пользователя из шаблона и склонируй его в выбранное место. Если шаблон открыт на GitHub, это одна команда: `gh repo create <имя> --private --template <шаблон> --clone`, затем перенос в нужный каталог. Если пользователь получил шаблон архивом, создай пустой приватный репозиторий и сделай первый коммит из содержимого архива.
2. Если штаб не в `~/HQ`, замени этот путь во всех текстовых файлах репозитория (`doctrine/`, `AGENTS.md`, `skills/`, `docs/`) и покажи пользователю дифф.
3. Включи секрет-гейт: `git config core.hooksPath .githooks`. На Windows проверь, что Git запускает хук через свой bash.
4. Заведи лейблы задач из раздела «Задачи» в `AGENTS.md` командой `gh label create` и лейбл `project:<slug>` на каждый проект из реестра.
5. Впиши проекты в `registry.md`.
6. Закоммить и запушь.

**Проверка.** Секрет-гейт: создай временный файл со строкой `AKIA` и шестнадцатью заглавными буквами или цифрами, добавь его в индекс и попробуй закоммитить. Коммит должен быть отклонён с сообщением «СЕКРЕТ-ГЕЙТ». Затем убери файл из индекса и удали. Лейблы: `gh label list` показывает все созданные. Push: `git status -sb` не показывает расхождения с origin.

## Фаза 2. Доктрина для всех агентов

Цель: каждый выбранный агент в любой сессии видит `doctrine/AGENTS.md`. Способ зависит от агента, и принцип один: ссылка на канон, а не копия (ADR-0002).

| Агент | Куда подключать | Как |
|---|---|---|
| Claude Code | `~/.claude/CLAUDE.md` | строка `@~/HQ/doctrine/AGENTS.md`; прежнее содержимое файла остаётся ниже |
| Codex | `~/.codex/AGENTS.md` (или в `$CODEX_HOME`) | символическая ссылка на `~/HQ/doctrine/AGENTS.md` |
| Другие агенты | их файл глобальных инструкций | импорт, если агент его понимает, иначе ссылка; сверь с документацией агента |

Этот шаблон проверялся на Claude Code и Codex. Для остальных агентов строка таблицы только подсказка, а решает проверка ниже.

Если у Codex уже был свой `~/.codex/AGENTS.md` с содержимым, ссылка его заменит. Перенеси это содержимое в подходящее место и покажи пользователю: личные правила общения в доктрину, особенности инструмента в `lessons/tools/codex.md`. Старый файл сохрани копией.

Где символические ссылки недоступны (Windows без режима разработчика), используй импорт, если агент его понимает, или копию с первой строкой «копия ~/HQ/doctrine/AGENTS.md, править там». Про такую копию скажи пользователю: её придётся обновлять после каждой правки канона.

**Проверка живой цитатой.** Агент, который «видит файл», ещё не получил правила; получил тот, кто может процитировать из них строку. В доктрине есть контрольное предложение, начинающееся словами «Прерывание владельцем»; оно встречается в тексте один раз. Запусти каждого агента неинтерактивно из нейтрального каталога, например домашнего, с таким запросом:

```
Не выполняй действий и не читай файлы. Процитируй дословно предложение из уже загруженных инструкций, которое начинается словами «Прерывание владельцем». Если его нет в контексте, ответь ровно: НЕТ ФРАЗЫ.
```

Для Claude Code это `claude -p "<запрос>"`, для Codex `codex exec --skip-git-repo-check -s read-only "<запрос>"`, для других агентов их неинтерактивный режим. Сделай это **до** подключения: ответ должен быть «НЕТ ФРАЗЫ». Так ты убедишься, что проверка умеет упасть. **После** подключения ответ должен быть дословной цитатой. Пересказ или список файлов успехом не считается.

## Фаза 3. Скиллы

Скиллы лежат в `~/HQ/skills/`: `recall` (поиск по памяти), `end-session` (выход из сессии), `backlog` (задачи). Подключи каждый к каждому агенту ссылкой на каталог скилла в каталоге скиллов агента. У Claude Code это `~/.claude/skills/<имя>`, у Codex `~/.codex/skills/<имя>`; для других агентов сверься с их документацией. На Windows вместо символической ссылки на каталог подойдёт junction (`mklink /J`), ему не нужны права администратора.

Если у пользователя уже есть скилл с таким именем, не заменяй его. Покажи оба и спроси.

**Проверка.** Спроси каждого агента неинтерактивно: «Перечисли доступные тебе скиллы, в которых есть слова recall, end-session или backlog. Если таких нет, ответь НЕТ.» До подключения ответ должен быть «НЕТ», после подключения должны быть названы все три.

## Фаза 4. Память на QMD

### 4.1. Установка QMD

Одна установка обслуживает всех агентов: `npm install -g @tobilu/qmd` (или `bun install -g @tobilu/qmd`). На macOS QMD требует SQLite из Homebrew: `brew install sqlite`. Если QMD уже стоит плагином одного из агентов, не ставь второй экземпляр: у разных агентов окажутся разные версии, а индекс общий. Выбери один и скажи пользователю, какой.

Проверка: `qmd --version` и `qmd status`.

### 4.2. Коллекции

Коллекция в QMD это папка с markdown, которую он индексирует. Заведи:

- по коллекции на историю каждого подключённого агента: `~/agent-memory/cc-history` с именем `cc-history`, `~/agent-memory/codex-history` с именем `codex-history`. Сначала создай пустые папки;
- штаб: `~/HQ` с именем `hq`;
- папки, которые пользователь назвал в фазе 0, например `docs/` проектов.

Команда: `qmd collection add <путь> --name <имя>`. Каждой коллекции добавь одну строку описания, чтобы агенту при поиске было понятно, что в ней лежит: `qmd context add qmd://<имя> "<что здесь лежит>"`. Например: «История сессий Claude Code: одна сессия — один файл, реплики владельца и ответы агента».

Каталог `~/agent-memory` можно перенести; тогда задай переменную `AGENT_MEMORY_DIR` везде, где запускается `sync.py`, и поправь пути коллекций. Устройство выгрузки описано в `memory/README.md`.

### 4.3. Первая выгрузка и индекс

1. `python3 ~/HQ/memory/sync.py --no-embed` выгружает все прошлые сессии и строит поиск по словам. На большой истории это минуты.
2. `qmd embed` считает векторы для поиска по смыслу. **Предупреди пользователя до запуска:** при первом запуске QMD скачивает три локальные модели, в сумме порядка двух гигабайт (размеры моделей приведены в README QMD), а сам расчёт на длинной истории занимает заметное время и нагружает процессор. Запускай в фоне и после его «ок».

Проверка: `python3 ~/HQ/memory/sync.py --status` показывает число выгруженных файлов, `qmd status` показывает документы в каждой коллекции, а `qmd search "<слово из недавней сессии>"` находит эту сессию.

### 4.4. QMD в агентах

QMD подключается к агенту как MCP-сервер командой `qmd mcp`.

- Claude Code: `claude mcp add qmd --scope user -- qmd mcp`. Есть и плагин (`claude plugin marketplace add tobi/qmd`, затем `claude plugin install qmd@qmd`), но он приносит свою копию QMD; см. 4.1.
- Codex: `codex mcp add qmd -- qmd mcp` или раздел `[mcp_servers.qmd]` с `command = "qmd"` и `args = ["mcp"]` в `~/.codex/config.toml`.
- Другие агенты: stdio-сервер с командой `qmd mcp`, по их документации.

Если агенту не виден `qmd` из-за урезанного PATH, укажи полный путь к нему. Каждый агент поднимает свой процесс QMD, и модели загружаются в каждом. Если агентов много и это тяжело, у QMD есть общий фоновый сервер `qmd mcp --http --daemon`; как к нему подключаться, описано в README QMD.

Проверка: спроси агента неинтерактивно «вызови инструмент status сервера qmd и перечисли коллекции». Он должен назвать коллекции из 4.2.

### 4.5. Автоматическая синхронизация

Память должна обновляться сама. Для этого одна команда `python3 ~/HQ/memory/sync.py` запускается двумя путями.

**Хук конца сессии.** Если у агента есть хук на конец сессии, повесь на него `python3 ~/HQ/memory/sync.py --detach`. Флаг `--detach` сразу возвращает управление, и сессия не ждёт индексации. У Claude Code это событие `SessionEnd` в `~/.claude/settings.json`. Существующие хуки пользователя сохраняются: добавляй свою группу рядом, а не заменяй массив. Есть ли такой хук у других агентов, проверь по их документации.

**Планировщик системы раз в час.** Он догоняет сессии, оборвавшиеся без конца, и агентов без хуков. Используй штатный механизм системы:

- macOS: агент launchd в `~/Library/LaunchAgents/` с `StartInterval` 3600, загружается через `launchctl bootstrap gui/<uid> <файл>`;
- Linux: пользовательские `systemd` service и timer, включаются через `systemctl --user enable --now <имя>.timer`; без systemd подойдёт `cron`;
- Windows: задание Планировщика заданий с ежечасным запуском.

Планировщики запускают задачи с урезанным окружением. `sync.py` сам ищет `qmd` и `node` в типовых каталогах, но надёжнее задать в задании переменную `QMD_BIN` с полным путём к `qmd` и полный путь к интерпретатору Python.

Проверка: `python3 ~/HQ/memory/sync.py --status` через час после установки показывает прогон, которого ты не запускал руками. Сквозная проверка хука: начни короткую сессию агента, напиши в ней выдуманное слово, которого нет больше нигде, закончи сессию, подожди минуту и найди это слово через `qmd search`. До конца сессии поиск не должен его находить.

## Фаза 5. Подключение рабочего проекта

Для каждого проекта, который пользователь хочет вести через штаб:

1. В корне проекта `AGENTS.md` с правилами именно этого проекта: как собирать и тестировать, что нельзя ломать, куда что класть. Если правила уже есть в `CLAUDE.md`, перенеси их в `AGENTS.md`, а в `CLAUDE.md` оставь одну строку `@AGENTS.md`. Внизу отметка `> _Last reviewed: <дата>_`. Если проект общий с командой, эти файлы коммитятся только с согласия пользователя.
2. Строка в `~/HQ/registry.md`, лейбл `project:<slug>`, при необходимости коллекция QMD на `docs/` проекта.

Проверка: та же живая цитата, что в фазе 2, но с фразой, которая есть только в `AGENTS.md` проекта, и запуском из каталога проекта.

## Фаза 6. Сводка пользователю

Отдай итог, который читается без переписки выше:

- что установлено и где лежит, списком «файл или настройка → зачем»;
- какие проверки прошли, с их результатом;
- что не проверено и почему;
- как этим пользоваться каждый день: три-четыре фразы из раздела «Как этим жить» в `README.md`;
- как откатить: список изменённых файлов и сделанных копий.

Проект этой настройки заведи первой задачей в беклоге штаба и закрой её итоговым комментарием после «ок» пользователя.

## Обновления шаблона

Если шаблон потом обновится, изменения подтягиваются как из второго удалённого репозитория: `git remote add template <адрес шаблона>`, `git fetch template`, `git merge template/main`. Файлы, которые пользователь правил под себя, особенно доктрина, могут дать конфликты. Разбирай их вместе с пользователем: его правки важнее.
