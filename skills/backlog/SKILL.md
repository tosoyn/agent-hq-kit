# Беклог штаба в GitHub Issues

Беклог живёт в GitHub Issues репозитория штаба `~/HQ`. Этот скилл задаёт порядок, как задачи показывать, добавлять, разбирать и закрывать. Правила самих задач (что заслуживает тикета, лейблы, вопросы владельцу) описаны в `~/HQ/AGENTS.md`, раздел «Задачи». Команды ниже выполняются из каталога `~/HQ`, поэтому `gh` сам знает репозиторий.

Всё, что пишет в GitHub, делается после черновика и явного «ок» владельца. Результат каждой записи перечитывается через `gh issue view`.

## Показать

```bash
gh issue list --state open --limit 100 --json number,title,labels,updatedAt
gh issue list --label needs-owner --json number,title,updatedAt
```

Выведи задачи, сгруппированные по `project:<slug>`: номер, заголовок, статус, приоритет. Отдельным блоком «ждут решения владельца» покажи тикеты с `needs-owner`, и для самого старого перескажи вопрос словами из последнего комментария. Ещё одним блоком «просрочено» покажи задачи, у которых в заголовке стоит «до ДД.ММ» с уже прошедшей датой: для каждой одной строкой, что осталось сделать, и предложи новый срок или закрытие.

## Добавить

1. Проверь, что это можно выполнить и закрыть. Направление, наблюдение или область тикетом не становятся; скажи об этом владельцу и предложи конкретный первый шаг.
2. Поищи дубль по смыслу, а не только по названию: `gh issue list --state all --search "<слова>"`. Найденное покажи владельцу.
3. Если описание размыто, задай два-три вопроса: какой результат, для какого проекта, по какому признаку готово.
4. Напиши черновик. Заголовок: суть задачи словами, срок строкой «до ДД.ММ», если он есть. Тело: зачем, что должно быть верно в конце (как проверить), шаги, если они известны, контекст и ссылки. Лейблы: `project:<slug>`, `status:new`, `priority:*`, `type:task` или `type:idea`. Если нужного лейбла проекта ещё нет, он тоже часть черновика, а проект получает строку в `registry.md`.
5. После «ок» создай задачу и перечитай её:
   ```bash
   gh issue create --title "<заголовок>" --body-file draft.md --label "project:<slug>,status:new,priority:normal,type:task"
   gh issue view <N>
   ```
   Номер задачи равен номеру Issue. Коммиты по ней получают префикс `[T-NNN]`.

## Разобрать

Разбор удобно делать раз в неделю. Он закрывает три очереди, которые без него только растут.

1. **Задачи.** Прочитай открытые задачи и разложи их на группы: делать сейчас, отложить, закрыть как сделанную, снять как неактуальную, обновить описание или срок.
2. **Идеи** (`type:idea`). Для каждой: берём в работу (лейбл меняется на `type:task`) или закрываем с причиной.
3. **Уроки.** Прочитай записи в `lessons/`, у которых ещё нет пометки о разборе. Для каждой предложи судьбу: перенести в правило (`AGENTS.md` проекта или доктрина, с текстом правки), считать устранённой, отменить. Порядок описан в `lessons/README.md`.

Покажи владельцу всё одним черновиком с причиной у каждого пункта. После «ок» примени: снятая задача закрывается с комментарием-причиной, а не удаляется; правки правил и пометки уроков коммитятся по скиллу `end-session`. В конце предложи одну задачу взять в работу.

## Закрыть

Задача закрывается только после приёмки владельцем. Подготовь итоговый комментарий: что сделано, ссылки на коммиты и результат, как проверено. После «ок» оставь комментарий и закрой:

```bash
gh issue comment <N> --body-file итог.md
gh issue close <N>
gh issue view <N>
```

Слово владельца о завершении сессии («закрой сессию», «выходим») уже считается приёмкой сделанного в этой сессии; тогда порядок ведёт скилл `end-session`.
